# README_DEPLOYMENT.md

## Назначение документа

Этот документ описывает порядок развёртывания HR Interview Assistant v2.0.0 в production-like окружении и подготовку проекта к размещению на хостинге производственного предприятия.

HR Interview Assistant рассматривается не как демонстрационный макет, а как рабочий web‑продукт, который после завершения выпускного проекта должен быть размещён на стороне предприятия и использоваться в пилотном формате.

## О проекте

**HR Interview Assistant** — это рабочий веб‑сервис для просмотра вакансий, прохождения структурированного интервью, server-side оценки кандидата через LLM, формирования отчётов и работы HR через защищённую панель.

Во второй версии проекта система уже поддерживает основной рабочий контур:
- просмотр материалов вакансии;
- прохождение интервью кандидатом;
- передачу структурированных ответов на backend;
- предварительную LLM‑оценку качества ответов;
- формирование markdown‑отчёта;
- предварительную рекомендацию для HR;
- HR‑панель для просмотра отчётов и управления карточками вакансий.

## Текущий стек

В проекте используется следующий стек:
- Python 3.11+;
- FastAPI;
- Jinja2 templates;
- HTML / CSS / JavaScript;
- Markdown- и YAML-файлы для карточек вакансий и отчётов;
- `.env` для конфигурации;
- SessionMiddleware для HR‑авторизации;
- uvicorn для запуска приложения;
- Nginx как reverse proxy;
- systemd для автозапуска сервиса.

## Контуры эксплуатации

Проект поддерживает два режима эксплуатации:

### Demo
Режим для учебной защиты, демонстрации и портфолио.

### Internal
Режим для последующего размещения на стороне предприятия с корпоративным брендингом, рабочими вакансиями, отчётами и настройками окружения.

При развёртывании на предприятии целевым должен считаться режим `internal`.

## Текущая структура интерфейса

В приложении используются следующие ключевые маршруты:

- `/` — главная страница;
- `/about` — информация о проекте;
- `/vacancies` — список вакансий;
- `/vacancies/{slug}` — карточка вакансии;
- `/interview?vacancyid=...` — страница интервью;
- `/report` — страница отчёта;
- `/hr/login` — вход в HR‑панель;
- `/hr` — HR‑панель;
- `/reports` — архив отчётов.

Перед production-развёртыванием необходимо убедиться, что все основные маршруты и кнопки работают корректно.

## Цель production-развёртывания

Цель развёртывания — разместить сервис на поддомене предприятия и обеспечить доступ к нему как к рабочему внутреннему или pilot‑продукту.

Примеры возможного размещения:
- `hr.company.ru`;
- `assistant.company.ru`;
- `interview.company.ru`.

С основного сайта предприятия должна вести ссылка на сервис, а в самом сервисе при необходимости должна быть доступна ссылка на основной сайт предприятия.

## Варианты размещения

## Вариант 1. Если хостинг не поддерживает Python

Если провайдер предоставляет только shared‑хостинг без поддержки Python‑приложений, можно разместить только статическую или демонстрационную часть интерфейса.

В этом случае ограничения будут следующими:
- FastAPI нельзя использовать как полноценный backend на данном хостинге;
- server-side логика интервью и LLM‑оценка потребуют отдельного backend‑сервера;
- frontend должен будет обращаться к backend API по HTTPS.

Такой вариант допустим только как временное решение. Для рабочего размещения версии 2.0.0 предпочтителен полноценный серверный запуск.

## Вариант 2. Полноценное развёртывание FastAPI

Этот вариант является целевым.

Он подходит, если есть:
- VPS;
- Linux‑сервер;
- внутренняя виртуальная машина предприятия;
- доступ для запуска Python‑приложения как сервиса.

В этом случае размещаются:
- FastAPI‑приложение;
- Jinja2‑шаблоны;
- static‑файлы;
- `.env` с параметрами окружения;
- reverse proxy через Nginx;
- systemd‑сервис;
- домен или поддомен предприятия.

## Рекомендуемая схема работы

1. Пользователь открывает домен сервиса, например `https://hr.company.ru`.
2. Nginx принимает входящий запрос.
3. Nginx проксирует запрос в `uvicorn`.
4. FastAPI обрабатывает frontend- и backend‑логику.
5. При необходимости backend обращается к внешнему LLM API.
6. Пользователь получает HTML‑страницы, результаты интервью и отчёты.

## Рекомендуемая структура проекта на сервере

```text
/opt/hr-assistant-backend/
├── app/
│   ├── main.py
│   ├── config.py
│   ├── llmservice.py
│   ├── templates/
│   ├── static/
│   ├── services/
│   └── data/
├── job_profiles/
├── reports/
├── logs/
├── requirements.txt
├── .env
├── .env.example
├── README.md
├── README_DEPLOYMENT.md
└── CHECKLIST_PRODUCTION.md
```

Фактическая структура каталогов может незначительно отличаться, но на сервере должны быть чётко разделены код приложения, конфигурация, данные вакансий, отчёты, логи и deployment‑документы.

## Минимальные требования к серверу

Для размещения необходимы:
- Ubuntu 22.04+ или аналогичный Linux;
- Python 3.11+;
- `pip`;
- `venv`;
- Nginx;
- systemd;
- SSL‑сертификат для домена или поддомена;
- доступ к настройке DNS;
- доступ к настройке переменных окружения и прав пользователей.

## Установка на Linux / VPS

### 1. Копирование проекта

Скопировать проект на сервер, например в каталог:

```bash
/opt/hr-assistant-backend
```

### 2. Создание виртуального окружения

```bash
cd /opt/hr-assistant-backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

### 3. Подготовка `.env`

Создать файл `.env` на сервере на основе `.env.example` и заполнить реальные значения.

Минимально должны быть настроены:

```env
HR_USERNAME=your_hr_login
HR_PASSWORD=your_hr_password
SESSION_SECRET_KEY=your-long-random-secret-key
LLM_PROVIDER=openai
LLM_TIMEOUT_SECONDS=60
OPENAI_API_KEY=your_openai_key
OPENAI_MODEL=your_model
OPENAI_BASE_URL=
GIGACHAT_API_KEY=
GIGACHAT_MODEL=
```

При использовании режима `internal` также должны быть настроены параметры брендинга, ссылок и корпоративного окружения.

### 4. Тестовый запуск приложения

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

После запуска необходимо убедиться, что приложение открывается по IP сервера и порту `8000`, а основные маршруты работают без критических ошибок.

### 5. Настройка systemd

Создать systemd‑сервис:

```text
/etc/systemd/system/hr-assistant.service
```

Пример содержимого:

```ini
[Unit]
Description=HR Interview Assistant
After=network.target

[Service]
User=www-data
Group=www-data
WorkingDirectory=/opt/hr-assistant-backend
Environment="PATH=/opt/hr-assistant-backend/venv/bin"
ExecStart=/opt/hr-assistant-backend/venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Команды управления сервисом:

```bash
sudo systemctl daemon-reload
sudo systemctl enable hr-assistant.service
sudo systemctl start hr-assistant.service
sudo systemctl status hr-assistant.service
```

### 6. Настройка Nginx

Создать конфигурационный файл, например:

```text
/etc/nginx/sites-available/hr.company.ru
```

Пример конфигурации:

```nginx
server {
    listen 80;
    server_name hr.company.ru;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

После этого выполнить:

```bash
sudo ln -s /etc/nginx/sites-available/hr.company.ru /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
```

### 7. Подключение HTTPS

Для production‑размещения необходимо включить HTTPS.

Можно использовать:
- `certbot` и Let's Encrypt;
- корпоративный SSL‑сертификат предприятия.

## Что проверить после установки

После размещения необходимо проверить:
- сайт открывается по домену;
- главная страница работает;
- список вакансий открывается;
- карточки вакансий открываются;
- сценарий интервью запускается;
- отправка интервью и обработка результата работает;
- отчёт сохраняется и открывается;
- `/hr/login` открывается;
- HR‑авторизация работает;
- HR‑панель открывается;
- архив отчётов доступен в штатном режиме;
- логи пишутся без критических ошибок;
- статические файлы, шаблоны, сессии и конфигурация загружаются корректно.

## Безопасность

Перед публикацией в production необходимо проверить:
- `.env` не хранится в Git;
- реальные секреты не попадают в репозиторий;
- включён HTTPS;
- debug‑режим отключён;
- права доступа к файлам и каталогам настроены корректно;
- HR‑доступ защищён;
- переменные окружения заполнены корректно;
- логи не раскрывают чувствительные данные.

## Подготовка к размещению на предприятии

Перед финальным размещением необходимо:
- привести репозиторий в чистый публикационный вид;
- убрать временные файлы, тестовые артефакты и локальные логи;
- проверить `.gitignore`;
- подготовить инструкции повторного деплоя;
- проверить корпоративный брендинг, фон, логотипы и ссылки;
- проверить работоспособность режима `internal`;
- подготовить демонстрационный и рабочий набор вакансий и отчётов.

## Практический итог

Для локальной демонстрации и выпускной защиты проект уже может использоваться как рабочая система.

Для полноценного размещения на стороне предприятия необходимы:
1. репозиторий проекта в финальном виде;
2. VPS, Linux‑сервер или корпоративная виртуальная машина с поддержкой Python;
3. настройка `uvicorn`;
4. настройка `systemd`;
5. настройка `nginx`;
6. подключение HTTPS;
7. проверка конфигурации, маршрутов, HR‑авторизации, LLM‑части и отчётности.
